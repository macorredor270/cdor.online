# M9 — Núcleo móvil Rust/SQLite

Estado: completado.

## Resultado

- SQLite 3 se compila embebido mediante `rusqlite 0.40.1`.
- Dos migraciones versionadas crean la réplica parcial, outbox y cursor.
- Conversaciones, mensajes, memorias y preferencias solo se leen/escriben
  desde repositorios Rust.
- La entidad offline y `pending_operations` se guardan atómicamente.
- El outbox deduplica por `operation_id`, aplica backoff con jitter de
  1 segundo a 5 minutos y detiene errores permanentes.
- `SyncEngine` usa traits de API, conectividad y secretos. El bearer no tiene
  almacenamiento SQLite y queda reservado para Keystore/Keychain en M10.
- Push aplicado/duplicado elimina el outbox; conflicto/rechazo queda bloqueado;
  pull reemplaza siempre con el estado MySQL y persiste cambios+cursor en una
  transacción.
- Un delete remoto domina la mutación local y un cursor caducado reinicia una
  única resincronización completa.
- El compilador C del NDK se exporta para los cuatro targets Android, necesario
  para enlazar SQLite embebido.

Las pruebas cubren cierre/reapertura, migraciones, rollback ante reutilización
incompatible, offline→online, deduplicación, backoff, error permanente,
prevalencia MySQL, delete y cursor inválido.

## Riesgos pendientes

- El núcleo es síncrono. M10 debe alojarlo en estado nativo y ejecutar acceso a
  disco/red fuera del hilo principal.
- WAL no se habilita hasta medir estabilidad tras interrupción en el Xiaomi.
- `SyncApi` y `SecretStore` son interfaces; HTTPS y Keystore/Keychain se
  conectan en M10, no se simulan como producción en M9.

## Condición exacta de detención

M9 se cierra cuando los tests reproducen offline→online, reinicio y
deduplicación, MySQL reemplaza el estado local, el outbox no reintenta errores
permanentes y el mismo núcleo compila para Android ARM64.
